Summary

AGI EXT is a presentation and interaction layer over agents-cli. The CLI owns every fact (sessions, devices, accounts, executions, teams, attention, activity) and every mechanism (launch, placement, resume, fork, stop, scheduling, watchdog). The extension owns editor tabs, webviews, the mapping between them, and local presentation preferences. Two rules follow: every live fact on screen arrives through one agents feed watch --json stream that exactly one elected editor window runs, and every user action leaves the extension as exactly one CLI verb. Missing facts are added to the CLI's stream row, never reconstructed from transcripts or fetched on a loop. The PRD states what the user gets; this document explains how the pieces produce it and where the code still falls short.

Read by question: ownership · runtime components · session projection · terminal lifecycle · launch composition · needs-you · module graph and debt · build, test, release.

System boundary and ownership

The CLI owns facts and mechanisms. The extension owns presentation: which tab is visible, sidebar layout, transient selection, and the restoration metadata needed to reopen a tab. When the UI needs a fact the stream lacks, the fact is added to the CLI's SessionWatchRow (backfilled from the index, the way version landed), never reconstructed from transcripts or fetched on a poll (the one exception, an explicit-click timeline filter, is described under the sidebar row below)ing loop. That side channel is how the 2026-08-25 CPU incident happened (agi-cli#3019).

Runtime components

The extension host is a single Node process per editor window. It holds the elected stream leader (or a follower client), the broadcast server or client, the window-local presentation store, the terminal registry, the command adapters, and the webview bridge. React webviews render serializable view models and post typed intent back; native VS Code APIs and CLI execution never leave the host.

Session projection

Exactly one elected window starts the long-lived child, and only while some window reports demand: a visible sidebar or Project Sessions tab, an open Resume picker, or a tracked agent tab whose identity the stream has not resolved yet. When no window demands it the producer is torn down after a 5 s debounce, so an idle window contributes no watcher. The leader normalizes newline-delimited events, keeps a replay cache so a window that gains demand paints current rows without waiting, and broadcasts each event to followers over the monitor socket. A child that keeps dying is respawned with exponential backoff up to 30 s, and its process group is torn down before a restart so an ssh descendant can never outlive it.

feed watch is the only producer of three things: session rows, attention.* (the sole input to needs-you), and activity.append. A cheaper local journal tail carries none of the attention or activity events and drops every remote session unless something replaces the fleet fan-out; switching to it is not a drop-in and stays blocked on the CLI side.

The row that reaches the sidebar carries the summarizer's goal, checkpoints, summaryChecklist, and summaryState, and the daemon-computed request, timeline, and files. src/core/remoteSessions.ts normalizes all of them at the boundary (2,000 request characters, 8 timeline steps, 8 file rows) and returns undefined for anything the CLI did not send, so an older CLI degrades to the documented fallbacks (request → userPromptClean → topic; timeline → checkpoints; files → nothing) instead of a guess.

The glance fields ride the same row: title (best source first), model, failures (newest 20, failed and blocked), activityHistogram (48 fixed buckets plus user-turn times, for the seek bar), userTurns, subagents, artifact titles joined from .artifact.json sidecars, and image attachments the CLI materialized under ~/.agents/.cache/attachments/. Artifacts carry editedAtMs for newest-first sorting. The sidebar webview's other image root is the home directory, fixed when the view is created (changing roots reloads a webview); it renders a thumbnail only for an image artifact the row names under home for a session on this machine. A remote session's artifacts show as file-type tiles; clicking one copies that single file into ~/.agents/.cache/remote-artifacts/<device>/ with one agents ssh <device> --argv call and opens the local copy in the Reader, because a vscode-remote:// URI fails without a Remote-SSH connection. A request's pasted images resolve by file name in this machine's ~/.agents/.history/attachments/, where the CLI saves them, so they show for remote sessions too. The request carries the owner's Gravatar (sha256(email), d=404, as artifacts-cli uses) over their initial. Each field is absent on an older CLI, and the sidebar then shows counts without lists, or nothing. Three timeline filters (agent messages, tool calls, reasoning) are too large for every row: each is one sessions <id> --include <role> --json call on an explicit click (the standalone sessions CLI, resolved like agents; tools answers with the tool-search envelope), cached in the webview per session and filter (marked stale with a Refresh link once newer activity arrives), never on selection or on a timer, and offered only for a session on this machine because sessions reads the local index. The host answers only a request whose session id is still the panel's subject; a failed load is shown and retried on the next click, never cached.

Failure semantics: a missing CLI binary is a visible prerequisite failure; a malformed feed event is rejected and reported without corrupting the current scope; loss of the leader triggers election and replay; missing facts render as unknown or degraded, and zero is reserved for known zero; a follower that has never observed a reset for a scope renders that scope as degraded; resolved attention cannot reappear from an older snapshot; a historical Previous row cannot reclaim a terminal already rebound to another live session on the same owner host.

Terminal lifecycle

An editor terminal has an extension-local id (CL-<ts>-<n>) before the harness reveals its native session id. Launch metadata and stream facts converge on the terminal registry; once correlated, the canonical CLI session id drives status, labels, resume, fork, stop, and Project panel focus. Labels have two classes: a canonical session-derived title and an explicit user label; the user label wins because it is presentation intent.

Every agent tab is opened by openTrackedTab (src/vscode/extension.ts): New Agent and its variants, the startup auto-open, /spawn, Resume, Reopen Last Closed Session, the resume launches, Fork, the queued launches (dispatch, Continue, Fork (Pick Session), the Reader's Send to Agent) and restore. It fixes the tab's identity at createTerminal (icon, name, an env scrubbed unless the tab is a New Shell, and AGENT_TERMINAL_ID/AGENT_SESSION_ID/AGENT_VERSION), waits at most 10 s for the shell pid (processIdWithin), registers the tab with the registry and readiness, and stamps the harness, host, version, account and session id before the label poller starts. Sending the launch line is sendCommandWhenReady (after promptReady), and a prompt for the agent is submitToTui: typed without a newline, then \r after 300 ms, because Ink TUIs take \r as Enter and a multi-line bracketed paste swallows one sent in the same tick. A tab the extension did not open (found on activation, or opened by the editor later) is registered by terminals.adopt from its creation env, with the persisted entry for its terminal id winning for labels, host, version and session; on activation a tab with no shell is closed so restore reopens its session.

Correlation is not launch-only. A user may stop session A and start session B in the same terminal, so the stable observer terminal id can appear on both rows while the feed settles. On each pushed reset or agent-row change the extension reconciles tracked tabs before the status bar or sidebar refreshes: it ignores Previous rows, treats two distinct live claims as ambiguous within the same observer-device and execution-host scope, and keeps the existing binding during the overlap. When A is removed, B becomes the sole claim and the tab rebinds; a later historical A upsert marked Previous cannot revert it. A terminal-selected sidebar subject stores the terminal's stable id and follows it across the rebind; a subject selected from the Project panel stays tied to its session.

The shell's AGENT_TERMINAL_ID remains stable across agents.clear and harness restarts. Every open tab with that id gets a live-terminals.json entry (src/vscode/terminalRegistry.vscode.ts) carrying the terminalId, the harness kind from the prefix in PRESENTED_AGENTS, and the shell pid. The launch sessionId is present only when the extension minted one (Claude); Codex, Grok and the rest pick their id after start, and the CLI joins those tabs by terminalId. The CLI, the file's only reader (viewing-in.ts, active.ts), dedupes by terminalId. A window's slice is pruned once its at is older than 10 minutes even when its pids are alive: live windows rewrite it every 4 minutes, and a reload writes under a new window id. Shell start time never proves session ownership. Reload restores a session id from the exact persisted terminal-id record before using the shell's frozen AGENT_SESSION_ID; it does not scan processes, read transcripts, or pick a recent same-prefix session. Focus hydration identifies unresolved tabs; corrections to established bindings run on pushed stream facts.

agents.setSessionId accepts { terminalId?: string }, defaults to the active agent terminal, and prefills the current id. It uses the existing canonical-id and hydration validators, calls the registry's setSessionId, and persists immediately. A manual id holds until a different session appears for that terminal; it survives reload. The tab persists the selected id and every superseded canonical id. Stream reconciliation filters those superseded claims for that tab before applying the same Previous, observer-device, execution-host, and ambiguity rules. A different eligible live claim replaces the binding and clears the override. Clear uses the same mechanism to exclude the pre-clear session. An exact persisted record is authoritative even when its id is empty, so reload leaves a cleared tab unbound until a different session appears. This uses only pushed stream facts; it starts no watcher, poller, subprocess, or transcript read.

Restoration metadata (~/.swarmify/agents/windows/<hash>.yaml, one file per window named by its workspace file or folder and replaced atomically, so no window can rewrite another's tabs: terminal id, prefix, session id, host, label, auto-label, harness, recovery harness, version, pid) is enough to reopen a tab through the CLI's resume path. Restore reopens one tab per session and none for a session the window already shows (restorePlan, src/core/sessions.persist.ts); a tab leaves the file the moment it closes for any reason but window shutdown. The scan snapshots the file before registering anything, so a write during a slow scan cannot erase tabs still waiting to be reopened. An empty or corrupt window file restores nothing; it never falls back to the old shared file. A session another live window shows is not reopened (liveWindows: the pid answers and the file was written since boot). Restore creates each tab hidden and shows it once its process runs: an editor-located terminal opened while the window is still starting is resolved as a text file and shows "The editor could not be opened". An agent terminal whose pty never came back is closed and its session reopens as a live tab. Restored, resumed and reloaded tabs run the resume as the tab's own process (agentTabShell), never typed at a prompt. Limits: a corrupt or empty window file restores nothing (its tabs are lost once, never replaced by the old shared file's); saving an untitled workspace changes its key, so its tabs are not restored that once; two windows on the same folder or workspace (which the editor normally prevents) share one file. On the first launch after the upgrade, each first-folder key of the old shared file is handed to one window only. It is never proof that a process is alive and never a transcript cache. Reload and user close are distinct: reload preserves the session; a genuine user close (TerminalExitReason.User, src/vscode/terminalReadiness.ts) issues one agents ps stop.

Launch command composition

Every Agents: New <Harness> variant routes through one engine (src/core/launchTarget.ts → src/core/agents.ts buildAgentLaunchCommand). The setting agents.launch.defaultTarget (auto default, local, ask) decides the plain command; the five explicit variants pin one axis each and never both.

(Pick Host) --device <name> --cwd <workspace> --strategy balanced --mode auto the account picker, --device auto

Bare interactive runs auto-place in agents-cli 1.22.118, so local placement must be explicit. Hostless version pins also emit --local to preserve their local intent; an explicit host takes precedence.

Every other launch goes through the same builder. buildTabLaunchCommand (src/core/launchTarget.ts) serves New Agent, its splits, aliases, quick-launch slots, the startup auto-open and Clear: --local, or --device <name> when the tab runs on a device, never --device auto, so Clear relaunches a tab where it was; always --cwd <workspace>. Shell and a user-defined custom agent are not CLI harnesses and keep their own command. Resume (Pick Harness) runs agents run <harness> on the session's device or --local; Resume in Best Profile runs agents run auto on the session's device or --device auto (which a bare run auto also means); both carry --cwd and no --strategy. Fork and Fork (Pick Host) are agents fork <id> [--device <host>] (forkCommand, src/core/forkSession.ts). The Reader's Send to Agent is a queued launch (openSingleAgentWithQueue) with --local and the selection as its prompt. Fork (Pick Session) still launches the harness in the picked session's folder through openSingleAgentWithQueue and types /continue <id>: agents fork starts the sibling in that folder only from agents-cli 1.23.27, and it has no --cwd to pass, so moving it would land a fork of another project's session in this window's folder on older CLIs.

Flag order is fixed by buildAgentLaunchCommand: agent spec, --interactive, --device or --local, --cwd or --project, --session-id (Claude), --strategy, --model, --mode; src/core/launchTarget.test.ts asserts these strings without a workspace. --strategy balanced is set for every variant except the account picker (src/core/launchTarget.ts strategy: options.accountPicker ? undefined : 'balanced') and is dropped for a pinned version, where the CLI would ignore it. The exclusions are thrown as errors inside buildAgentLaunchCommand: cwd with remoteCwd, project with either cwd form, the account picker with a pinned version, the account picker with a strategy. --cwd is emitted once, independent of placement, because the terminal's inherited process.cwd() can differ from the active folder. --session-id is emitted for Claude, and for auto, which applies it only when it picks Claude. Ordinary launches never derive a target from agents projects view <cwd>: that command is a containment attribution lookup and a shared root can belong to several child projects (PHNX-3970). Native-mode launches are wrapped by wrapNativeAgentCommand so exit code 0 closes the tab and the CLI's ssh-loss codes (255, 254) read as a recoverable reconnect rather than a crash.

Needs-you attention as pure projection

The Project panel's pinned "Needs you" group is a projection of the CLI attention rows the stream carries (RemoteAttention in src/core/remoteSessions.ts, joined onto their session in sessionPresentationStore.sessions()). Membership is attention.state === 'open'. Order comes from attention.kind through attentionRank (ATTENTION_KIND_RANK) in src/shared/sessionState.ts: question, permission, plan_review, declared, failure, stall, review. The Active Session sidebar shows the same open item under its header in the harness's own words, with Reply and Focus. A stall is a CLI signal: sessionStateOf reads it as Stopped and SessionStateKey has no stalled member. A tab the stream has not indexed carries no attention and never enters the group from the client side.

Project attribution follows the same rule: the Project panel filters on the CLI's own confirmedProject (projectSessions in src/core/projectPanel.ts). One stopgap until agents-cli resolves a renamed project's old names: a row whose checkout (its cwd, a worktree folded to its repository) is one of the project's own repository paths is shown too, only when its confirmedProject is empty or not a registered project (projectFallback, the registry cached a minute in src/vscode/projectRegistry.vscode.ts); the resume picker applies the same rule. That compares against paths the CLI gave for the project; it never guesses a project name from a cwd, and it goes away when the feed carries aliases.

⌘K (agents.searchSessions) reads nothing. ProjectView.openPalette brings the Project panel up on Sessions (its own view, or the window it popped out into) and posts renderPalette (src/core/projectPanel.ts): every session the presentation store holds, any project, live and ended, in paletteOrder (favorites, asks by the CLI's urgency then wait, running and waiting, idle newest first, ended last and capped at 150). Each row carries what the store already gave the cards: the PRs and pages it made (sessionMade), the images the request attached (requestImageThumbs, the attachments folder the webview may read) and its recap's first sentence. While the overlay is open its rows follow every Sessions redraw. The page filters in place with paletteMatch, interpolated into its script (exact id first, then title prefix, title words, other words), and Enter is one paletteGo: a tab here comes forward as a card click does, anything else goes where its focus or resume icon would. VS Code's QuickPick was dropped because it re-sorts by its own label match and can neither align a row's details nor show an image.

The rest of the Project panel composes the same way. Session rows describe conversations and progress; attention facts keep the exact question, choices, and resolution lifecycle; activity facts supply chronological evidence such as plans, pull requests, teams, and artifacts. The panel may group, filter, sort, and decorate them, and must never infer a new canonical status from transcript text or process scans. Its overview, pull request, and ticket tabs arrive through separate bounded CLI reads and do not live in the presentation store. Optimistic UI is limited to transient feedback; durable changes arrive back through the feed.

Findings

The leader's monitor broadcast socket binds through listenOwned in src/monitor/endpoint.ts: listen on a private path, then link() it to the shared path, which fails instead of replacing a live server. A leftover path is removed only when nothing accepts on it. Close unlinks the shared path only while it is still this server's inode, and destroys every accepted connection so teardown never waits on a peer. Because the path is reachable before MonitorHost.start() settles, the host re-evaluates demand reported in that window once it runs.

Monitor frames are structurally validated before delivery. A complete valid frame has the same result whether received whole, coalesced, or fragmented. Incomplete-frame buffering remains unbounded: the CLI producer defines no maximum reset size, so a consumer-only cap would silently lose legitimate session facts. A shared producer/consumer size contract is required before adding that bound.
